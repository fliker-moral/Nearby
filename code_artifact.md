# Архитектура проекта: Волонтерский Mini App (MAX Ecosystem)

Данный документ описывает системную архитектуру, стек технологий, доменную модель, механизмы безопасности и правила взаимодействия компонентов для сервиса помощи и организации волонтёрских мероприятий на базе платформы **MAX Mini Apps**.

---

## 1. Обзор системы и ключевые цели

Приложение представляет собой интерактивную карту в формате Mini App для мессенджера **MAX**, объединяющую авторов заявок (заявителей/организации) и волонтёров.

### Ключевые требования:
* **Интеграция с экосистемой MAX:** Работа через **MAX Bridge (JS SDK)** для получения контекста мессенджера, шэринга, нативной навигации и аутентификации через **MAX WebAppData**.
* **Интерактивная гео-карта:** Поиск и фильтрация задач по видимой области экрана (Bounding Box) и выбранным районам.
* **Реактивность (Real-Time):** Мгновенное обновление статуса меток на карте у всех активных пользователей через WebSockets.
* **Атомарный захват задач (Atomic Task Assignment):** Исключение состояния гонки (Race Condition), когда несколько волонтёров одновременно пытаются откликнуться на одно задание.
* **Готовность к горизонтальному масштабированию (Horizontal Scaling Ready):** Безликое (stateless) API, распределенная трансляция WebSocket-событий через Redis Pub/Sub и пулинг соединений с БД.
* **Медиафайлы:** Загрузка фотографий задач и фотоотчётов через S3-совместимое хранилище.
* **Модерация и роли:** Разграничение прав доступа (RBAC) и пре-модерация контента перед публикацией.
* **Система рейтинга:** Оценка профиля по 5-балльной шкале и качественным тегам («Отзывчивость», «Пунктуальность»).
* **Запуск «в один клик»:** Изоляция всех сервисов в Docker Compose для гарантированного запуска на чистом ПК.

| Слой / Компонент | Технология | Назначение |

| **Frontend / SDK** | **React / MAX Bridge SDK** | Клиентское Mini App, взаимодействие с нативным клиентом MAX Messenger. |

| **Оркестрация** | **Docker Compose / Nginx** | Единый контейнерный запуск и балансировка нагрузки. |

## 4. Авторизация и аутентификация через MAX Auth

Аутентификация строится на базе **MAX WebAppData** и не требует формы ввода логина/пароля.

### Схема аутентификации:
1. **MAX Mini App (Frontend)** при старте получает строку `initData` через `MAX Bridge` (`window.MAX.WebApp.initData`).
2. Клиент передает эту строку в заголовке `Authorization: Bearer <initData>` при каждом HTTP/WS запросе.
3. **Backend (FastAPI)** валидирует подпись `initData` с использованием HMAC-SHA256 и секретного токена бота MAX:
   * Извлекается хэш `hash` из строки `initData`.
   * Из остальных параметров формируется строка проверки `data_check_string`.
   * Вычисляется секретный ключ: $secret\_key = HMAC\_SHA256("WebAppData", bot\_token)$.
   * Вычисляется контрольный хэш: $calculated\_hash = HMAC\_SHA256(secret\_key, data\_check_string)$.
   * Если $calculated\_hash == hash$, данные пользователя считаются валидными.
4. Профиль пользователя автоматически создается или обновляется в БД (UPSERT по `max_id`).

* `assigned_volunteer_id` (UUID, FK -> `User.id`, Nullable)
* `title` (String)
* `description` (Text)

* `location` (Geometry(Point, 4326)) — Координаты точки на карте
* `address_text` (String) — Читаемый адрес/ориентир
* `photos` (Array[String]) — Ссылки на фотографии
* `completion_photo` (String, Nullable) — Фотоотчет волонтёра
* `version` (Integer, Default: 1) — Поле оптимистичной блокировки (при необходимости)
* `created_at` (DateTime)

#### 3. `Review` (Отзывы и Оценки)
* `id` (UUID, Primary Key)
* `task_id` (UUID, FK -> `Task.id`)
* `author_id` (UUID, FK -> `User.id`)
* `target_user_id` (UUID, FK -> `User.id`)
* `score` (Integer, 1-5)
* `tags` (Array[String]) — Выбранные качества (например, `["доброта", "пунктуальность"]`)
* `comment` (Text, Nullable)

## 6. Механизм атомарного назначения задач (Atomic Task Assignment)

Для предотвращения **Race Condition** (когда двое или более волонтеров нажимают кнопку «Взять задачу» одновременно) применяется атомарное условие на уровне СУБД с префиксной блокировкой/проверкой условий.

### Реализация через условный SQL UPDATE (Рекомендуемый подход)
Назначение задачи происходит с помощью единого запроса, проверяющего статус и факт отсутствия назначенного исполнителя прямо во время выполнения транзакции:

```sql
UPDATE tasks
SET 
    assigned_volunteer_id = :volunteer_id,
    status = 'IN_PROGRESS'
WHERE 
    id = :task_id 
    AND status = 'PUBLISHED' 
    AND assigned_volunteer_id IS NULL;
```

### Логика обработки на Backend:
1. Выполняется запрос `UPDATE`.
2. Анализируется количество обновленных строк (`affected_rows` / `rowcount`):
   * **Если `rowcount == 1`:** Захват задачи прошёл успешно. Задача переведена на волонтёра. Сервер генерирует событие `TASK_STATUS_CHANGED` в Redis Pub/Sub.
   * **Если `rowcount == 0`:** Задача уже взята другим волонтёром либо отменена. Пользователю возвращается ошибка `HTTP 409 Conflict` с понятным сообщением («К сожалению, эту задачу уже взял другой волонтёр»).

## 7. Горизонтальное масштабирование и Real-Time (WebSockets)

Для обеспечения высокой доступности и устойчивости к нагрузкам система спроектирована по принципу **Stateless Architecture**.

```text
               [ Клиент А ]             [ Клиент B ]
                    │                        │
                    ▼                        ▼
           ┌─────────────────┐      ┌─────────────────┐
           │ Backend Node 1  │      │ Backend Node 2  │
           └────────┬────────┘      └────────┬────────┘
                    │                        ▲
             1. Publish                      │ 2. Broadcast
                    │                        │
                    ▼                        │
          ┌────────────────────────────────────┐
          │         Redis Pub/Sub Channel      │
          └────────────────────────────────────┘
```

### 1. Масштабирование WebSockets через Redis Pub/Sub
* Серверные экземпляры (Nodes) FastAPI не хранят клиентские состояния в оперативной памяти глобально.
* Каждый экземпляр отслеживает список локально подключенных к нему сокетов.
* При изменении статуса задачи (например, при атомарном захвате) узел, обработавший запрос, публикует событие в канал Redis `map_updates`.
* Все узлы бэкенда подписаны на `map_updates`. При получении события каждый узел рассылает его только своим подключенным WebSocket-клиентам, попадающим в Bounding Box события.

### 2. Подключение к БД и Connection Pooling
* Для предотвращения исчерпания лимита соединений PostgreSQL при увеличении числа узлов FastAPI используется встроенный асинхронный пулинг (`asyncpg` / `SQLAlchemy AsyncEngine`) или прокси-сервер **PgBouncer**.

### Подключение
`WS /api/v1/ws/map?bbox=min_lon,min_lat,max_lon,max_lat&token=<MAX_WebAppData>`

### События (Payload Examples)
* **Новая метка на карте:**
  ```json
  {
    "event": "TASK_CREATED",
    "data": {
      "task_id": "uuid",
      "lat": 55.751244,
      "lon": 37.618423,
      "category": "PERSONAL_HELP",
      "title": "Помочь донести продукты"
    }
  }
  ```
* **Задание взято волонтером (скрыть/изменить цвет метки):**
  ```json
  {
    "event": "TASK_STATUS_CHANGED",
    "data": {
      "task_id": "uuid",
      "new_status": "IN_PROGRESS"
    }
  }
  ```

## 10. Автоматизация развертывания и масштабирование (Docker Setup)

Запуск базовой инфраструктуры производится единой командой:

```bash
docker compose up --build -d
```

Для проверки горизонтального масштабирования (запуск 3 экзепляров бэкенда за балансировщиком Nginx):

```bash
docker compose up --build -d --scale backend=3
```

### Автоматический порядок запуска:
1. Поднятие `db` (Postgres + PostGIS) и `redis`.
2. Ожидание готовности БД через `healthcheck`.
3. Запуск реплик `backend` и выполнения скрипта `entrypoint.sh`:
   * Выполнение `alembic upgrade head` (создание таблиц и пространственных индексов).
   * Инициализация S3-бакетов в MinIO.
   * Сидинг тестового администратора и начальных данных.
   * Старт Uvicorn сервера.
4. Запуск `nginx` балансировщика, распределяющего трафик между узлами `backend`.
